Introducción

Las restricciones de integridad definen el conjunto de estados que un esquema relacional puede admitir. Son el mecanismo mediante el cual el sistema evita que los datos representen una realidad imposible, inconsistente o ambiguamente interpretada.

El diseño correcto combina restricciones declarativas con reglas de negocio que pueden requerir lógica procedural. La diferencia clave es que una regla declarativa se valida por el motor de base de datos de manera uniforme, mientras que una regla de transición exige comparar el estado anterior y el nuevo valor antes de aceptar el cambio.

Tipos de restricciones

  • NOT NULL: impide valores faltantes donde el dominio requiere información.
  • UNIQUE: garantiza unicidad en columnas o grupos de columnas.
  • PRIMARY KEY: identifica cada fila con unicidad y no nulidad.
  • FOREIGN KEY: exige que la relación referencial exista en la tabla padre.
  • CHECK: valida condiciones booleanas sobre filas o registros.
  • ASSERTION: regla global que involucra múltiples tablas.

Integridad referencial

Una llave foránea no es solo una restricción técnica: representa una obligación semántica entre dos entidades. Si una fila padre se elimina o actualiza, la base de datos debe decidir cómo responder con ON DELETE y ON UPDATE.

Las opciones CASCADE, RESTRICT, SET NULL y SET DEFAULT reflejan decisiones de negocio distintas. En un modelo bien diseñado, la opción elegida debe ser coherente con la semántica del dominio y con la historia que se quiere preservar.

Restricciones de transición

Las reglas de transición dependen del cambio entre estados. Por ejemplo, “el sueldo no puede disminuir” o “el stock no puede quedar negativo sin una compensación explícita” no son verificables con una sola fila aislada, sino con el valor anterior y el nuevo valor.

Estas reglas suelen implementarse con triggers o lógica procedural porque requieren observación del contexto y del evento. Cuando la regla puede expresarse declarativamente, la solución es más robusta y más fácil de mantener.

Recomendación práctica

  • Usar restricciones declarativas siempre que la regla correspondiente se pueda expresar en DDL.
  • Reservar triggers para aspectos dinámicos o de negocio que involucren contexto previo.
  • Diseñar con consistencia y semántica, no solo con “que la base no falle”.
