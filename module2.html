Fundamento formal de las restricciones

Sea un esquema relacional R y sea I una instancia posible de sus relaciones. Una restricción de integridad C define qué instancias son admisibles: I es válida si y solo si I satisface C. Toda transacción debe transformar una instancia válida en otra válida al llegar al punto de comprobación. La base de datos ejecuta esa comprobación dentro de la operación transaccional; si falla, se rechaza la sentencia o la transacción según el momento de evaluación, evitando que una aplicación pueda omitir la regla.

Las restricciones describen invariantes, no secuencias de pasos. Preferir la forma declarativa permite al optimizador y al motor conocer la regla, mantenerla en cargas masivas y escrituras concurrentes, y reportar de forma uniforme la violación. La lógica procedural se reserva para reglas que dependen de una transición, de agregados entre filas o de acciones que no se pueden representar con constraints nativas.

Restricciones de dominio, fila y clave

NOT NULL exige presencia; CHECK exige que una expresión booleana no sea FALSE. En PostgreSQL, un CHECK que evalúa UNKNOWN por NULL se considera satisfecho: por tanto, CHECK (edad >= 18) no reemplaza a NOT NULL si la edad es obligatoria. El constraint se comprueba al insertar o actualizar la fila afectada.

UNIQUE exige que los valores de una columna o combinación no se repitan. En PostgreSQL, por defecto los NULL no se consideran iguales para UNIQUE, así que pueden existir múltiples NULL; versiones recientes permiten expresar NULLS NOT DISTINCT. Una clave primaria equivale a identificación única y no nula; una tabla tiene una sola primary key, aunque puede tener varias claves candidatas mediante UNIQUE.

Las claves compuestas representan unicidad del conjunto ordenado de atributos, no la unicidad individual de cada componente. Los nombres explícitos de constraints facilitan migraciones y diagnósticos.

CREATE TABLE departamento (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre text NOT NULL UNIQUE
);

CREATE TABLE empleado (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    departamento_id bigint NOT NULL,
    correo text NOT NULL,
    salario numeric(12, 2) NOT NULL,
    activo boolean NOT NULL DEFAULT true,
    CONSTRAINT empleado_salario_no_negativo CHECK (salario >= 0),
    CONSTRAINT empleado_correo_unico UNIQUE (correo),
    CONSTRAINT empleado_departamento_fk
        FOREIGN KEY (departamento_id) REFERENCES departamento(id)
);

DEFAULT solo aporta un valor cuando se omite la columna o se solicita DEFAULT; no prohíbe NULL ni reemplaza NOT NULL. Un CHECK opera normalmente sobre la fila actual y no debe usarse para consultar otras filas: el motor no garantiza que una condición interfilas escrita así se mantenga ante escrituras concurrentes.

Una constraint local como NOT NULL o CHECK se comprueba al procesar cada fila afectada, por lo que su trabajo es normalmente proporcional al número de filas modificadas. UNIQUE y PRIMARY KEY requieren detectar duplicados; PostgreSQL mantiene un índice único, con búsqueda típica O(log n) por fila y costo adicional de espacio, WAL y mantenimiento. Las referencias requieren localizar claves padre y al modificar/borrar un padre también identificar hijas; indexar la columna de la foreign key evita a menudo un recorrido completo de la tabla hija.

Integridad referencial y acciones referenciales

Una foreign key de una tabla hija a una clave primaria o UNIQUE de una tabla padre requiere que cada valor no nulo de la referencia coincida con una fila padre. Para una referencia opcional, NULL expresa que no existe asociación; en una referencia obligatoria se agrega NOT NULL. Una foreign key compuesta con MATCH SIMPLE (predeterminado) no exige coincidencia si algún componente es NULL; MATCH FULL permite todos NULL o todos no nulos, no una mezcla.

Las acciones determinan el efecto de cambiar o borrar una fila referenciada: NO ACTION comprueba la regla en el momento de validación y puede diferirse; RESTRICT impide la operación inmediatamente; CASCADE propaga actualización o borrado a hijas; SET NULL o SET DEFAULT sustituyen los valores, siempre que el resultado satisfaga el resto de constraints. Cascadas pueden atravesar varias tablas y causar efectos extensos dentro de la misma transacción; deben reflejar dependencia semántica real, no ser un atajo de limpieza.

En PostgreSQL, las foreign keys se verifican mediante mecanismos internos de integridad y bloqueos que coordinan transacciones concurrentes. Un índice en las columnas hijas no es creado automáticamente por la foreign key, pero suele ser necesario para localizar eficientemente las filas afectadas al borrar o actualizar al padre.

ALTER TABLE empleado
    ADD CONSTRAINT empleado_departamento_fk
    FOREIGN KEY (departamento_id)
    REFERENCES departamento(id)
    ON UPDATE CASCADE
    ON DELETE RESTRICT;

Restricciones diferibles, globales y de transición

Algunas reglas solo pueden comprobarse cuando una operación compuesta termina. PostgreSQL permite declarar ciertos constraints como DEFERRABLE INITIALLY IMMEDIATE o INITIALLY DEFERRED; con SET CONSTRAINTS ... DEFERRED se pospone la comprobación hasta el final de la transacción. CHECK no es diferible en PostgreSQL; UNIQUE, PRIMARY KEY y FOREIGN KEY sí pueden serlo si se declaran DEFERRABLE, con limitaciones específicas. Las restricciones diferibles no pueden servir como objetivo de ciertas cláusulas ON CONFLICT.

El estándar SQL contempla ASSERTION para invariantes globales que pueden involucrar varias tablas, pero PostgreSQL no implementa CREATE ASSERTION. Si una regla global es realmente necesaria, hay que diseñarla con cuidado: restricciones únicas, exclusion constraints, modelado que haga la condición local, o triggers con bloqueo/aislamiento adecuado. Un trigger que solo consulta “si existe” y luego inserta puede sufrir una carrera: dos transacciones pueden observar que la condición se cumple y violarla simultáneamente. Debe usarse una constraint nativa, bloquear una clave común, o serializar/gestionar conflictos transaccionales de forma explícita.

Las reglas de transición comparan el estado anterior y el nuevo, por ejemplo “un saldo no puede disminuir” o “el estado solo puede avanzar por transiciones permitidas”. Un CHECK puede imponer el rango actual del saldo, pero no el historial de cambio; se requiere trigger o registrar cada transición. En un trigger de fila, OLD contiene la fila anterior y NEW la propuesta nueva.

Selección del mecanismo y diagnóstico

Modele cada regla primero como predicado: ¿atañe a un valor, a una fila, a la unicidad entre filas, a una referencia, al conjunto global o al paso entre dos estados? Use respectivamente NOT NULL/DEFAULT, CHECK, UNIQUE/EXCLUDE, FOREIGN KEY, una constraint global nativa o una solución transaccional procedural. Las constraints deben llevar nombres estables y probarse tanto en inserciones como en modificaciones, borrados, cargas masivas y escrituras simultáneas.

Una violación aborta la sentencia o puede dejar la transacción en estado de error hasta hacer ROLLBACK o SAVEPOINT recovery. No se debe ocultar el error en la aplicación y continuar como si se hubiera persistido el dato. Mantenga la validación en la base aunque la interfaz también valide: la interfaz mejora la experiencia, pero no controla todos los clientes ni las carreras entre procesos.
