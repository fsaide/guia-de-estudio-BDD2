Módulo 7: Seguridad y control de acceso

La seguridad de la información exige controlar quién puede leer, escribir, modificar o administrar cada objeto del sistema, evitando la exposición innecesaria de datos y los accesos no autorizados.

Introducción

La seguridad en una base de datos no es un agregado opcional ni una capa superficial. Determina qué usuarios y roles pueden acceder a cada objeto, bajo qué condiciones, y qué tipo de operaciones pueden ejecutar. La política de seguridad debe seguir el principio de menor privilegio: cada usuario recibe únicamente el acceso necesario para cumplir su función.

La administración de permisos es central para proteger la confidencialidad, la integridad y la disponibilidad de la información. Si los privilegios se conceden de forma indiscriminada, la base de datos queda expuesta a accesos no autorizados, manipulación accidental o pérdida de control administrativo.

Privilegios y roles

Se distinguen permisos sobre objetos y permisos sobre operaciones. Por ejemplo, un usuario puede tener derecho a consultar una tabla, insertar filas, modificar determinadas columnas o eliminar registros. Cuando se administran muchos usuarios con funciones similares, es conveniente agrupar esos permisos mediante roles.

Un rol permite centralizar la política de acceso y simplificar la gestión. En lugar de asignar permisos directamente a cada persona, el administrador crea roles con funciones específicas y luego les asigna esos roles a los usuarios correspondientes.

GRANT y REVOKE

La asignación de permisos se realiza con GRANT, mientras que la retirada se hace con REVOKE. La sintaxis formal del estándar SQL define qué objeto recibe el permiso, qué privilegio se otorga y si el usuario beneficiario puede a su vez conceder ese privilegio a terceros.

La cláusula WITH GRANT OPTION es importante porque modifica la capacidad de delegación: el receptor del privilegio puede posteriormente concederlo a otros usuarios. Esa funcionalidad debe analizarse con cuidado porque puede producir cascadas de permisos difíciles de gestionar y auditar.

Seguridad mediante vistas

Las vistas son una herramienta muy útil para restringir el acceso directo a tablas completas. Se puede crear una vista que muestre solo columnas relevantes o filas autorizadas y conceder permisos sobre esa vista en lugar de sobre la tabla base. Esto ayuda a encapsular el esquema interno y evitar que un usuario vea información sensible o no requerida.

Cuando la lógica de negocio exige ocultar información confidencial, una vista puede ser la capa adecuada de seguridad. La idea es que el usuario interactúe con los datos que necesita y no con la estructura completa del sistema.

Inyección SQL

La seguridad de acceso no se agota en permisos del sistema. La inyección SQL aparece cuando una aplicación concatena cadenas ingresadas por el usuario dentro de una sentencia SQL sin validación ni parametrización adecuada. El atacante puede manipular la consulta e intentar leer, modificar o borrar datos.

La prevención es clara: usar consultas parametrizadas, validar entradas, no confiar en información externa y diseñar la base como un entorno accesible solo a través de mecanismos controlados. La seguridad del diseño debe contemplar tanto la autorización del usuario como la protección del código de acceso a datos.
