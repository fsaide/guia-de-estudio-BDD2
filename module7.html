Módulo 7: Seguridad y control de acceso

La seguridad de la información exige controlar quién puede leer, escribir, modificar o administrar cada objeto del sistema, evitando la exposición innecesaria de datos y los accesos no autorizados.

Introducción

El control de acceso determina qué principal autenticado puede realizar qué operación sobre qué objeto. La autenticación verifica la identidad; la autorización decide las acciones permitidas. El motor combina privilegios de roles, permisos de objetos, atributos y políticas de fila para controlar conexiones, esquemas, tablas, secuencias, funciones y otros objetos.

El principio de menor privilegio concede solo las capacidades indispensables, durante el tiempo necesario y a través de roles específicos. Separe identidades humanas, roles de aplicación y cuentas administrativas; evite compartir superusuarios; audite quién puede conceder privilegios y quién puede ejecutar código con permisos elevados. La seguridad debe proteger confidencialidad, integridad y disponibilidad, y debe comprobarse con la identidad real que usará la aplicación.

Privilegios y roles

En PostgreSQL, un rol puede iniciar sesión si tiene atributo LOGIN; los roles sin LOGIN se usan habitualmente como grupos de privilegios. Las membresías conectan roles y permiten heredar privilegios según las opciones de membresía y la configuración. El rol activo puede cambiar mediante SET ROLE. El propietario de un objeto posee capacidades que no se reducen a un GRANT común, por lo que conviene separar un propietario sin LOGIN del usuario de aplicación.

Los privilegios incluyen CONNECT sobre base de datos; USAGE sobre esquema (permite resolver nombres, no acceder por sí solo a las tablas); SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES y TRIGGER sobre tablas; permisos por columna para ciertos privilegios; y USAGE/SELECT/UPDATE sobre secuencias. Crear un esquema o tabla requiere capacidades distintas a consultarlos. El rol especial PUBLIC representa todos los roles; una concesión a PUBLIC debe tratarse como amplia.

Este patrón separa el propietario de los roles de lectura y escritura; los nombres deben adaptarse al despliegue:

CREATE ROLE datos_owner NOLOGIN;
CREATE ROLE app_lectura NOLOGIN;
CREATE ROLE app_escritura NOLOGIN;
CREATE ROLE app_login LOGIN;

GRANT app_lectura, app_escritura TO app_login;
GRANT CONNECT ON DATABASE tienda TO app_login;
GRANT USAGE ON SCHEMA public TO app_lectura, app_escritura;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_lectura;
GRANT SELECT, INSERT, UPDATE, DELETE
    ON ALL TABLES IN SCHEMA public TO app_escritura;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_escritura;

Las concesiones sobre objetos existentes no cubren automáticamente los futuros: configure privilegios por defecto para el rol que los crea y el esquema. Revise privilegios efectivos con \dp/\du en psql o los catálogos y pruebe con una sesión del rol consumidor, no solo como administrador.

GRANT y REVOKE

La asignación de permisos se realiza con GRANT, mientras que la retirada se hace con REVOKE. La sintaxis formal del estándar SQL define qué objeto recibe el permiso, qué privilegio se otorga y si el usuario beneficiario puede a su vez conceder ese privilegio a terceros.

GRANT privilegios ON objeto TO rol [WITH GRANT OPTION] crea una concesión. La opción permite que el receptor delegue ese privilegio; no transfiere la propiedad del objeto. En PostgreSQL, la retirada usa REVOKE [GRANT OPTION FOR] privilegios ON objeto FROM rol [CASCADE|RESTRICT]. CASCADE también revoca concesiones que dependían de la retirada; RESTRICT falla si existen concesiones dependientes.

GRANT SELECT ON TABLE public.pedido TO app_lectura;
GRANT UPDATE (estado) ON TABLE public.pedido TO app_escritura;
REVOKE ALL ON TABLE public.pedido FROM PUBLIC;

ALTER DEFAULT PRIVILEGES FOR ROLE datos_owner IN SCHEMA public
    GRANT SELECT ON TABLES TO app_lectura;

La concesión por columna limita qué atributos se pueden modificar, pero no sustituye políticas de fila ni evita que otros privilegios habiliten una ruta indirecta. Las secuencias y tablas tienen ACL independientes; con columnas identity/serial puede requerirse permiso sobre la secuencia. ALTER DEFAULT PRIVILEGES se aplica a objetos futuros creados por el rol indicado, no modifica los existentes ni establece una regla universal para objetos creados por otros propietarios.

Seguridad mediante vistas

Una vista puede proyectar columnas no confidenciales y filtrar filas autorizadas; se concede acceso a ella y se revoca el acceso directo a la tabla base. En PostgreSQL, las vistas ordinarias comprueban por defecto el acceso a relaciones subyacentes usando los permisos del propietario de la vista. Las versiones que admiten la opción security_invoker pueden comprobar permisos y RLS como el invocador. security_barrier restringe reordenamientos de predicados que podrían filtrar información mediante funciones no confiables, a costa de limitar optimizaciones.

Para control por fila, PostgreSQL ofrece Row-Level Security (RLS): ALTER TABLE ... ENABLE ROW LEVEL SECURITY activa políticas y CREATE POLICY especifica qué filas pueden leerse o modificarse mediante USING y WITH CHECK. Cuando RLS está habilitada y no hay política aplicable, el acceso normal se deniega. Los propietarios omiten RLS salvo que se use FORCE ROW LEVEL SECURITY; superusuarios y roles BYPASSRLS también la eluden. No conecte la aplicación como propietario o superusuario si depende de RLS para separar usuarios.

Una política añade la evaluación de sus predicados a las operaciones sobre filas y puede aumentar CPU, especialmente en scans amplios o con funciones costosas. Mantenga simples las expresiones, evite consultas correlacionadas repetidas y cree índices en las claves usadas por filtros selectivos cuando el plan pueda aprovecharlos; una política no transforma por sí sola una consulta O(n) en acceso selectivo.

ALTER TABLE pedido ENABLE ROW LEVEL SECURITY;
CREATE POLICY pedido_por_cliente
    ON pedido
    FOR SELECT
    USING (cliente_id = current_setting('app.cliente_id', true)::bigint);

El ejemplo solo es seguro si el valor del contexto de sesión no puede ser falsificado por el usuario final. Un parámetro de configuración personalizado no prueba por sí mismo la identidad. Diseñe el origen del contexto, el pool de conexiones y la política contra suplantación. Pruebe SELECT, INSERT, UPDATE y DELETE por separado: USING filtra las filas a las que aplica una operación; WITH CHECK valida las filas resultantes.

Inyección SQL

La inyección ocurre cuando datos externos se concatenan como parte de la sintaxis de una sentencia. La defensa principal es usar consultas parametrizadas para que el motor trate esos valores como datos, no como operadores o fragmentos SQL. La validación de dominio, autorización por objeto/fila y mínimo privilegio complementan la parametrización; escapar caracteres manualmente no es una defensa general.

-- La aplicación prepara esta consulta y envía el valor por separado.
PREPARE pedidos_cliente(bigint) AS
    SELECT id, creado_en, estado
    FROM pedido
    WHERE cliente_id = $1;

EXECUTE pedidos_cliente(42);

Los parámetros representan valores, no identificadores ni palabras clave. Para elegir dinámicamente una columna o dirección de orden, use una lista permitida en la aplicación y construya identificadores con el mecanismo seguro del driver, manteniendo los valores parametrizados. Los procedimientos almacenados también pueden ser vulnerables si construyen SQL dinámico por concatenación.

Use cuentas distintas por servicio, limite permisos de lectura/escritura, proteja credenciales y conexiones, audite cambios de roles/privilegios y registre actividad relevante sin almacenar secretos ni datos sensibles innecesarios. Aplique parches y proteja las copias de seguridad. Una consulta parametrizada no autoriza automáticamente a ver todas las filas: autenticación, autorización y validación son controles distintos.
