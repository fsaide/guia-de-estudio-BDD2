Modelo de vista y expansión de consultas

Una vista ordinaria es un objeto de catálogo cuyo cuerpo es una consulta almacenada. No mantiene una copia de las filas: al consultarla, el sistema combina su definición con la consulta externa y planifica la expresión resultante sobre las tablas base. Así, una vista ofrece un esquema lógico estable, permite reutilizar joins y expresiones, y separa las interfaces de lectura de la organización física.

La vista no congela resultados ni crea por sí sola una frontera de rendimiento. Si su definición contiene joins o agregaciones costosos, cada consulta puede volver a pagar ese costo. Las vistas anidadas pueden ser expandidas por el optimizador, pero una definición compleja puede dificultar la estimación o inspección del plan.

Por tanto, una vista común tiene el costo asintótico y de I/O de la consulta expandida, no O(1) por el hecho de estar nombrada. Una materializada cambia ese intercambio: el refresco debe leer y calcular el conjunto resultante (como mínimo proporcional a las filas examinadas y producidas), mientras que una lectura indexada puede localizar una clave en O(log n) y reduce trabajo repetido a costa de espacio y datos potencialmente atrasados.

Definición, reemplazo, dependencias y control de filas

La forma básica es CREATE [OR REPLACE] VIEW nombre [(columnas)] AS consulta [WITH [CASCADED|LOCAL] CHECK OPTION]. Las columnas de salida deben tener nombres únicos y tipos determinables. CREATE OR REPLACE VIEW conserva el objeto existente y sus permisos, pero en PostgreSQL no permite cambiar arbitrariamente nombres, tipos u orden de columnas existentes; ciertos cambios requieren recrearla y gestionar dependencias. DROP VIEW ... RESTRICT falla si hay dependientes; CASCADE los elimina también y debe usarse de forma deliberada.

CREATE VIEW empleados_activos AS
SELECT id, nombre, departamento_id
FROM empleado
WHERE activo
WITH LOCAL CHECK OPTION;

WITH CHECK OPTION impide insertar o actualizar, a través de esa vista, una fila que deje de satisfacer su condición de filtrado. LOCAL exige verificar la condición de la vista actual; CASCADED verifica también las condiciones de vistas subyacentes. Sin esta cláusula puede ser posible modificar una fila a través de la vista y que desaparezca de ella inmediatamente, aunque el cambio sea válido en la tabla.

El privilegio SELECT sobre una vista puede exponer solo las columnas y filas proyectadas. Para que sea un límite de seguridad efectivo, el rol consumidor no debe conservar acceso directo a las tablas base. En PostgreSQL, tenga en cuenta el comportamiento de permisos del propietario de la vista y la opción security_barrier cuando expresiones no confiables puedan revelar datos por canales laterales mediante evaluación de predicados. Una vista no sustituye políticas RLS para aislamiento por fila cuando esas políticas son el mecanismo apropiado.

Actualización a través de vistas

Una vista es automáticamente actualizable si el motor puede mapear cada fila visible a una fila de una tabla base y cada columna escrita a una columna base. En PostgreSQL, las vistas simples sobre una sola relación suelen ser actualizables; expresiones calculadas, agregaciones, DISTINCT, GROUP BY, ventanas y combinaciones complejas limitan esa posibilidad. Las reglas exactas del motor deben verificarse para la definición concreta.

Para una vista no actualizable, un trigger INSTEAD OF puede implementar INSERT, UPDATE o DELETE y traducir la operación a tablas base. El trigger debe definir claramente qué significa actualizar columnas derivadas, cómo manejar conflictos y qué fila devuelve. También puede usarse el sistema de rules, aunque los triggers suelen ofrecer un control procedural más explícito. Operaciones multi-tabla en vistas join pueden ser ambiguas; se debe elegir una tabla destino y conservar las restricciones de integridad.

Las vistas actualizables no permiten eludir las constraints de las tablas: cualquier escritura traducida se valida normalmente al llegar a la base. Si la aplicación necesita escribir varias tablas en una unidad lógica, encapsule los pasos en una función/procedimiento transaccional o en un trigger claramente definido.

Vistas materializadas, refresco y costo

Una vista materializada almacena físicamente el resultado de una consulta. CREATE MATERIALIZED VIEW nombre AS consulta puede calcular el contenido inicial; posteriormente REFRESH MATERIALIZED VIEW nombre vuelve a ejecutar la consulta y reemplaza los datos almacenados. No se actualiza automáticamente cuando cambia una tabla base, por lo que su frescura depende de la frecuencia y éxito del refresco.

La consulta de lectura puede acceder a los datos materializados como a una relación, y se le pueden crear índices. El refresco tradicional puede bloquear lecturas durante parte del reemplazo. REFRESH MATERIALIZED VIEW CONCURRENTLY permite lecturas concurrentes, pero requiere un índice UNIQUE que cubra todas las filas y use solo columnas (sin predicado parcial ni expresión), además de que la vista ya esté poblada. No elimina el costo de recalcular el resultado y necesita más recursos temporales.

CREATE MATERIALIZED VIEW ventas_por_mes AS
SELECT date_trunc('month', fecha) AS mes,
       producto_id,
       SUM(cantidad) AS unidades
FROM venta
GROUP BY date_trunc('month', fecha), producto_id;

CREATE UNIQUE INDEX ventas_por_mes_clave
    ON ventas_por_mes (mes, producto_id);

REFRESH MATERIALIZED VIEW CONCURRENTLY ventas_por_mes;

El trade-off consiste en desplazar CPU/I/O a la tarea de refresco y aceptar obsolescencia controlada para acelerar lecturas repetidas. Evalúe la duración del refresco, ventana de frescura, uso de disco, concurrencia y necesidad de incrementos. PostgreSQL no proporciona mantenimiento incremental general nativo de materialized views.

Diseño pragmático y límites

Use vistas para presentar contratos de lectura coherentes, ocultar columnas, encapsular expresiones repetidas y reducir el acoplamiento al esquema interno. Otorgar acceso a una vista y no a la tabla permite mínimo privilegio, pero la seguridad depende de los permisos efectivos y de la configuración del propietario. Versione los cambios de definición junto con la aplicación y pruebe dependencias antes de reemplazar o borrar objetos.

Use una vista ordinaria cuando los datos deben reflejar siempre el estado actual y el costo de consulta es aceptable; use una materializada cuando muchas lecturas repetidas justifican almacenamiento y una política de refresco; use una función o trigger INSTEAD OF cuando se necesite una interfaz de escritura no representable mediante actualización automática. No cree vistas solo para prometer velocidad: confirme el plan de ejecución y el costo real.
