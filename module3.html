Módulo 3: Vistas

Una vista es una tabla virtual cuyo contenido está definido por una consulta SELECT almacenada. No almacena datos por sí misma (a menos que sea una vista materializada), sino que muestra dinámicamente los datos de las tablas base subyacentes cada vez que se consulta.

Ventajas y Creación

  • Ventajas Principales:
    • Simplificación: Ocultan la complejidad de consultas que involucran múltiples tablas o cálculos complejos, presentando una interfaz más simple a los usuarios.
    • Seguridad: Permiten restringir el acceso a datos sensibles ocultando columnas específicas o filtrando filas según ciertos criterios. Los permisos (GRANT/REVOKE) se pueden aplicar directamente sobre las vistas.
    • Independencia Lógica: La estructura de las tablas base puede modificarse (hasta cierto punto) sin afectar a las aplicaciones o usuarios que acceden a los datos a través de vistas, siempre que la interfaz de la vista se mantenga.
  • Creación:

    Se utiliza la sentencia CREATE VIEW:

    CREATE [OR REPLACE] VIEW nombre_vista [(col1, col2, ...)] AS consulta_select [WITH [CASCADED | LOCAL] CHECK OPTION];
    • OR REPLACE: Permite modificar una vista existente sin necesidad de eliminarla primero.
    • (col1, col2, ...): Opcionalmente, permite renombrar las columnas resultantes de la consulta. Es obligatorio si hay columnas duplicadas o calculadas sin alias en la consulta.
    • consulta_select: Cualquier consulta SELECT válida que define el contenido de la vista. Puede basarse en una o más tablas, o incluso en otras vistas.
    • WITH CHECK OPTION: Se explica más adelante, previene la "migración de tuplas".
  • Eliminación: DROP VIEW nombre_vista [CASCADE | RESTRICT];
    • CASCADE: Elimina la vista y cualquier objeto dependiente de ella (como otras vistas).
    • RESTRICT (por defecto): Rechaza la eliminación si otros objetos dependen de la vista.

Vistas Actualizables

Realizar operaciones DML (INSERT, UPDATE, DELETE) directamente sobre una vista no siempre es posible. Para que una vista sea automáticamente actualizable, el SGBD debe poder mapear inequívocamente la operación sobre la vista a una operación sobre una única tabla base subyacente.

  • Condiciones Generales (Estándar SQL) : Una vista sobre una tabla es actualizable si, entre otras cosas: no usa DISTINCT , no usa funciones de agregación , no usa GROUP BY, e incluye todas las columnas NOT NULL sin valor por defecto de la tabla base (o al menos las que no se provean en el `INSERT`). Para vistas con `JOIN`, la actualización solo suele permitirse sobre la tabla que "preserva la clave".
  • Condiciones Específicas en PostgreSQL: PostgreSQL es más restrictivo. Una vista es automáticamente actualizable si:
    • Tiene exactamente una entrada en la cláusula FROM (que debe ser una tabla o una vista actualizable).
    • El SELECT de nivel superior no contiene: WITH, DISTINCT, GROUP BY, HAVING, LIMIT, OFFSET, operaciones de conjunto (UNION, INTERSECT, EXCEPT), funciones de agregación, funciones de ventana, o funciones que retornen conjuntos.

    Las columnas calculadas en una vista actualizable son de solo lectura.

  • Migración de Tuplas y WITH CHECK OPTION : Si se actualiza una fila a través de una vista de tal manera que ya no cumple la condición WHERE de la vista, esa fila "desaparece" de la vista (aunque sigue existiendo en la tabla base). Para evitar esto, se usa WITH CHECK OPTION. Esta cláusula hace que el SGBD rechace cualquier INSERT o UPDATE que resulte en una fila que no satisfaga la condición WHERE de la vista.
    • CASCADED (por defecto): Comprueba la condición de la vista actual y de todas las vistas subyacentes.
    • LOCAL: Comprueba la condición de la vista actual y solo de las vistas subyacentes que también tengan WITH CHECK OPTION.

Vistas Materializadas

A diferencia de las vistas estándar, una vista materializada almacena físicamente el resultado de su consulta, como si fuera una tabla real. Se crean principalmente por razones de rendimiento.

  • Ventajas: Consultar una vista materializada es mucho más rápido que ejecutar la consulta compleja subyacente cada vez, especialmente si la consulta es costosa (joins complejos, agregaciones sobre muchas filas). Se pueden crear índices sobre ellas.
  • Desventajas: Los datos almacenados pueden quedar desactualizados respecto a las tablas base. Requieren un mecanismo para refrescar (actualizar) su contenido, lo cual consume recursos. El refresco puede ser completo (recalcular todo) o incremental, y puede hacerse manualmente o de forma programada.
  • Uso: Comunes en almacenes de datos (Data Warehouses) y aplicaciones de Business Intelligence (BI) para precalcular sumarios y agregaciones.

Información Adicional Clave

Solución a Vistas no Actualizables: INSTEAD OF Triggers

Cuando una vista es compleja (ej: con `JOINs`, agregaciones, etc.) y no es actualizable automáticamente según las reglas del SGBD, puedes definir un trigger de tipo INSTEAD OF sobre ella. Este trigger intercepta la operación DML (INSERT, UPDATE o DELETE) dirigida a la vista y, en lugar de ejecutar la operación (que fallaría), ejecuta el código que tú definas dentro del trigger. Esto te da control total para describir manually cómo se deben modificar las tablas base subyacentes para reflejar la operación deseada sobre la vista. Es una forma potente pero compleja de dotar de comportamiento de actualización a vistas que de otro modo serían de solo lectura.

Vistas y Seguridad a Nivel de Fila (Row-Level Security - RLS)

Aunque las vistas pueden filtrar filas usando `WHERE`, una técnica más avanzada y flexible para la seguridad a nivel de fila es RLS (soportada por SGBD modernos como PostgreSQL). RLS permite definir políticas de seguridad directamente en las tablas, que filtran automáticamente las filas visibles o modificables basándose en el usuario actual o su rol, sin necesidad de crear múltiples vistas. Sin embargo, las vistas siguen siendo útiles para seguridad a nivel de columna o para simplificar accesos.
