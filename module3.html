SQL declarativo y procedural

El SQL declarativo especifica qué relación debe obtenerse o qué cambio se solicita. Un lenguaje procedural permite expresar una secuencia de instrucciones, variables, condiciones, iteraciones y manejo de errores. En PostgreSQL, PL/pgSQL integra esa lógica con SQL: se usa para funciones, procedimientos y funciones de trigger.

La lógica del servidor se ejecuta cerca de los datos y puede evitar múltiples viajes de red, centralizar reglas compartidas por distintos clientes y realizar operaciones atómicas dentro de una transacción. A cambio, aumenta el acoplamiento al motor, puede ocultar efectos laterales y añade trabajo a la ruta de escritura. Una constraint declarativa sigue siendo preferible cuando expresa completamente la regla: el motor puede optimizarla y hacerla cumplir incluso ante concurrencia.

El patrón ECA describe un trigger: un Evento (INSERT, UPDATE, DELETE o TRUNCATE), una Condición opcional y una Acción. La acción ocurre como parte de la misma transacción que originó el evento; si falla y no se captura, también falla la operación que disparó el trigger.

Triggers: momento, granularidad y ejecución

PostgreSQL separa la función del trigger de su asociación con una tabla. La función se declara RETURNS trigger; el trigger determina los eventos y cuándo llamarla. BEFORE permite modificar NEW antes de almacenar una fila o devolver NULL para omitirla; AFTER observa el cambio ya aplicado lógicamente y es adecuado para auditoría o efectos transaccionales derivados; INSTEAD OF sustituye la operación sobre una vista. Los triggers sobre tablas no admiten INSTEAD OF.

FOR EACH ROW invoca la función una vez por fila afectada; FOR EACH STATEMENT una vez por sentencia, incluso si afecta cero filas. En triggers de fila, OLD representa la versión anterior y NEW la propuesta nueva; su disponibilidad depende del evento: INSERT tiene NEW, DELETE tiene OLD y UPDATE tiene ambos. En triggers de sentencia no existen estas filas individuales; PostgreSQL puede exponer tablas de transición para determinados triggers AFTER, lo que permite procesar en conjunto todas las filas de la sentencia.

CREATE OR REPLACE FUNCTION normalizar_correo()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.correo := lower(trim(NEW.correo));
    RETURN NEW;
END;
$$;

CREATE TRIGGER empleado_normalizar_correo
BEFORE INSERT OR UPDATE OF correo ON empleado
FOR EACH ROW
EXECUTE FUNCTION normalizar_correo();

En un trigger BEFORE de fila, retornar NEW continúa la operación con la fila modificada; retornar OLD en UPDATE puede sustituir el resultado por la fila anterior; retornar NULL cancela esa fila sin abortar necesariamente las otras. En un trigger AFTER el valor de retorno se ignora. En INSTEAD OF se retorna la fila que representa la operación completada o NULL si no se procesó.

Un trigger puede emitir DML que dispare otros triggers. Diseñe una cadena acíclica o controle la condición de reentrada; la recursión accidental puede causar resultados duplicados o exceder límites de ejecución. Los triggers se disparan en un orden determinado por el motor (en PostgreSQL, por nombre para triggers del mismo evento/momento), pero no conviene usar ese detalle como sustituto de una transacción de negocio explícita.

Funciones, procedimientos y estructura de PL/pgSQL

Una función se crea con CREATE FUNCTION nombre(parámetros) RETURNS tipo LANGUAGE plpgsql y debe producir un resultado con RETURN, RETURN NEXT o RETURN QUERY, según su tipo. Puede invocarse como parte de una expresión SQL y no debe ejecutar control transaccional. Una función con efectos laterales no debe declararse falsamente IMMUTABLE o STABLE; esa volatilidad informa al optimizador sobre la posibilidad de cambios observables. STRICT indica que el motor no invoca la función si algún argumento es NULL.

Un procedimiento se define con CREATE PROCEDURE y se invoca mediante CALL; no tiene valor de retorno como una función, aunque admite parámetros OUT/INOUT. En PostgreSQL puede controlar transacciones con COMMIT/ROLLBACK en contextos permitidos: no puede hacerlo si el CALL está dentro de un bloque de transacción explícito, ni desde cualquier cadena de invocación que no permita control transaccional.

Un bloque PL/pgSQL tiene forma [<<etiqueta>>] [DECLARE ...] BEGIN ... END. Variables se declaran con tipo; asignaciones usan :=; control de flujo utiliza IF/ELSIF/ELSE, CASE, LOOP, WHILE y FOR. SELECT ... INTO variable asigna una fila; INTO STRICT exige exactamente una. Para DML, RETURNING ... INTO captura valores modificados. Si se requiere ejecutar SQL dinámico, use EXECUTE con USING para parametrizar valores y format('%I', identificador) para construir identificadores correctamente: los parámetros no reemplazan nombres de tabla o columna.

CREATE OR REPLACE FUNCTION salario_medio(p_departamento bigint)
RETURNS numeric
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
    v_promedio numeric;
BEGIN
    SELECT AVG(salario)
    INTO v_promedio
    FROM empleado
    WHERE departamento_id = p_departamento
      AND activo;

    RETURN v_promedio;
END;
$$;

La función devuelve NULL si el grupo no contiene salarios no nulos; no sustituye silenciosamente esa ausencia por cero. Para capturar errores, PL/pgSQL ofrece bloques BEGIN ... EXCEPTION WHEN condición THEN ... END. El bloque con EXCEPTION forma una subtransacción: las modificaciones realizadas dentro de él se revierten si ocurre la excepción, mientras el manejador puede registrar o traducir el error. No capture WHEN OTHERS para ignorar fallos; si se captura, vuelva a lanzar con RAISE cuando no exista una recuperación real.

Atomicidad, rendimiento y criterios de diseño

Funciones, procedimientos llamados desde una transacción y triggers participan del contexto transaccional del cliente: COMMIT confirma tanto el cambio original como sus efectos; ROLLBACK los revierte juntos. Bloqueos tomados por sus sentencias permanecen hasta terminar la transacción. Un trigger por fila agrega trabajo aproximadamente proporcional al número de filas afectadas; un trigger de sentencia evita repetir inicialización, y el procesamiento set-based suele superar un bucle fila a fila.

Use constraints para reglas locales; procedimientos para operaciones de negocio nombradas que coordinan varios pasos; funciones para cálculos o resultados invocables desde SQL; triggers para invariantes inevitables al escribir desde múltiples canales, auditoría transaccional o adaptación de vistas. Evite esconder llamadas remotas, lógica extensa o cambios no documentados en triggers. Documente el orden, permisos de ejecución y tablas modificadas.

Considere el privilegio de ejecución: por defecto, una función puede ejecutarse con los permisos del invocador (SECURITY INVOKER). SECURITY DEFINER corre con los del propietario y requiere especial cuidado: fije un search_path seguro, califique objetos, limite EXECUTE y no permita que entradas controladas por usuarios alteren la resolución de nombres. Pruebe rollback, múltiples filas, ausencia de filas, errores, cascadas y concurrencia; una prueba en una sola sesión no detecta todas las carreras.
