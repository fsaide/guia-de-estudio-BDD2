Introducción: consultas como expresiones relacionales

Una consulta SQL describe el resultado requerido y no prescribe, en general, el algoritmo físico para obtenerlo. El estándar combina operaciones sobre conjuntos o multiconjuntos de filas: selección (filtrado), proyección (elección de atributos), combinación, agrupación y ordenamiento. El optimizador puede transformar la expresión en otra equivalente y escoger accesos físicos distintos, siempre que conserve la semántica observable.

Las tablas SQL normalmente tienen semántica de multiconjunto: dos filas con los mismos valores pueden aparecer más de una vez. DISTINCT cambia explícitamente esa semántica al eliminar duplicados, lo que puede requerir ordenar o construir una estructura de hashing. El orden de las filas no está definido sin ORDER BY; un plan que hoy devuelve un orden aparente no constituye garantía.

Los costos concretos dependen del plan y el almacenamiento, no solo de la notación SQL: ordenar n filas suele costar O(n log n), mientras que agrupación/deduplicación por hashing tiene costo esperado O(n) y memoria O(n). Ambas estrategias pueden desbordar memoria y usar almacenamiento temporal. Un índice compatible puede evitar un ordenamiento, pero mantenerlo también cuesta en escrituras.

La forma general de una consulta de selección es SELECT [DISTINCT] expresiones FROM fuentes WHERE predicado GROUP BY claves HAVING predicado_de_grupo ORDER BY expresiones LIMIT cantidad OFFSET desplazamiento. Cada cláusula tiene restricciones de alcance: por ejemplo, WHERE filtra filas de entrada y no puede filtrar directamente un agregado calculado después de agrupar.

Orden lógico de evaluación y alcance

El orden lógico explica la visibilidad de nombres y los resultados, aunque no obliga al motor a ejecutar físicamente cada paso en ese orden. Conceptualmente se construyen las fuentes de FROM y sus joins; WHERE descarta filas; GROUP BY forma grupos; HAVING descarta grupos; SELECT calcula las expresiones de salida; DISTINCT elimina duplicados; ORDER BY ordena y, finalmente, OFFSET/LIMIT restringen el resultado.

En PostgreSQL, los nombres definidos en la lista de SELECT no están disponibles en WHERE, porque este se evalúa lógicamente antes. El alias suele estar disponible en ORDER BY. El orden físico elegido por el optimizador puede adelantar filtros o cambiar el orden de joins si demuestra que el resultado es equivalente.

SELECT d.nombre, COUNT(*) AS cantidad
FROM departamento AS d
JOIN empleado AS e ON e.departamento_id = d.id
WHERE e.activo
GROUP BY d.id, d.nombre
HAVING COUNT(*) >= 5
ORDER BY cantidad DESC, d.nombre;

El predicado sobre e.activo selecciona filas antes de agrupar. La condición sobre la cantidad se evalúa después de formar cada grupo. El segundo criterio de orden resuelve empates para que la salida sea determinista.

Predicados, NULL, agregación y ventanas

Lógica de predicados y valores ausentes

SQL usa lógica de tres valores: un predicado puede ser TRUE, FALSE o UNKNOWN. Las comparaciones ordinarias con NULL producen UNKNOWN; por ello columna = NULL no encuentra las filas nulas. Se usa IS NULL, IS NOT NULL o, cuando la regla pide comparar nulos como equivalentes, IS NOT DISTINCT FROM. En un WHERE solo sobreviven las filas cuyo predicado sea TRUE. NOT UNKNOWN sigue siendo UNKNOWN, detalle que afecta expresiones con NOT IN.

BETWEEN a AND b incluye ambos extremos; LIKE interpreta % como cualquier secuencia y _ como un carácter, con reglas de escape y collation dependientes del motor. IN expresa pertenencia; con elementos nulos puede dar UNKNOWN. EXISTS comprueba si la subconsulta produce al menos una fila y es la forma segura para muchas búsquedas de existencia.

Agregados y agrupación

GROUP BY particiona las filas por igualdad de las claves agrupadas. Cada grupo produce una fila de salida; las expresiones seleccionadas deben estar agrupadas, ser agregados o depender funcionalmente de las claves según las reglas del motor. COUNT(*) cuenta filas; COUNT(col) omite valores NULL; SUM, AVG, MIN y MAX también ignoran NULL y devuelven NULL si no hay valores aplicables. COALESCE permite especificar un valor sustituto explícito.

Funciones de ventana

Una función de ventana calcula sobre un marco de filas relacionadas sin colapsar el detalle como lo hace GROUP BY. La sintaxis es funcion(...) OVER ([PARTITION BY ...] [ORDER BY ...] [ROWS|RANGE|GROUPS ...]). PARTITION BY define grupos independientes; ORDER BY define la secuencia dentro de cada grupo; el marco determina qué filas participan en el cálculo de la fila actual.

SELECT empleado_id, departamento_id, salario,
       RANK() OVER (
           PARTITION BY departamento_id
           ORDER BY salario DESC
       ) AS puesto,
       AVG(salario) OVER (
           PARTITION BY departamento_id
       ) AS promedio_departamental
FROM empleado;

ROW_NUMBER asigna números únicos; RANK deja huecos tras empates y DENSE_RANK no los deja. LAG/LEAD consultan filas vecinas y SUM(...) OVER (... ORDER BY ... ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) calcula acumulados. Si el marco no se especifica, los valores por defecto con ordenamiento pueden producir acumulados por pares de empate; definir ROWS explícitamente evita ambigüedad cuando se requiere una fila física a la vez.

Joins, subconsultas, CTE y operadores de conjunto

INNER JOIN conserva solo pares que satisfacen la condición; LEFT, RIGHT y FULL OUTER JOIN preservan además las filas no coincidentes de uno o ambos lados y completan con NULL las columnas faltantes. CROSS JOIN genera el producto cartesiano: con entradas de tamaños m y n puede producir m×n filas. La condición de unión expresa la relación lógica y debe escribirse en ON; los filtros que deben conservar las filas sin pareja se colocan cuidadosamente, pues moverlos a WHERE puede convertir en la práctica un outer join en inner join.

Una subconsulta escalar debe producir como máximo un valor; una subconsulta tabular puede usarse con IN, ANY, ALL o EXISTS. Una subconsulta correlacionada refiere columnas de la consulta externa y tiene semántica por fila, aunque el optimizador puede transformarla en semi-join o anti-join. Para expresar “no existe”, NOT EXISTS evita la trampa de UNKNOWN de NOT IN cuando el conjunto contiene NULL.

Los operadores de conjuntos exigen igual cantidad de columnas y tipos compatibles por posición. UNION elimina duplicados; UNION ALL los conserva; INTERSECT devuelve la intersección y EXCEPT la diferencia. La deduplicación implica trabajo adicional. Una CTE (WITH) asigna nombre a una subconsulta para hacer legible y modular el cálculo; una CTE recursiva usa una parte inicial y otra recursiva unidas con UNION ALL para recorrer jerarquías o grafos. Su materialización o inlineado depende del motor y las opciones usadas, por lo que no se debe asumir que siempre materializa.

WITH RECURSIVE organigrama(id, jefe_id, nivel) AS (
    SELECT id, jefe_id, 0 FROM empleado WHERE id = 10
    UNION ALL
    SELECT e.id, e.jefe_id, o.nivel + 1
    FROM empleado AS e
    JOIN organigrama AS o ON e.jefe_id = o.id
)
SELECT id, jefe_id, nivel FROM organigrama ORDER BY nivel, id;

Construcción correcta y lectura pragmática

Use alias explícitos, califique columnas ambiguas y liste las columnas necesarias. Defina un orden total cuando el consumidor dependa de paginación: ORDER BY fecha, id es estable si id desempata. LIMIT/OFFSET con desplazamientos grandes puede obligar a recorrer y descartar muchas filas; la paginación por clave (keyset) evita ese costo cuando el orden tiene claves estables.

Verifique la cardinalidad prevista de los joins: una relación uno-a-muchos multiplica filas, por lo que sumar una medida del lado “uno” tras unir sin controlar la cardinalidad puede duplicar el total. Use una agregación previa o una consulta de existencia cuando la intención sea filtrar y no combinar columnas. Compare planes con EXPLAIN (ANALYZE, BUFFERS) en el módulo de optimización; las consultas correctas deben primero preservar el significado del dato y luego optimizarse.
